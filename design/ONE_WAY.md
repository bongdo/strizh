# Strizh — один канонический способ

**Статус:** концепция для 1.0. Это не описание 0.2: где текущая реализация
расходится с концепцией, это сказано явно.
**Связано:** [SPEC.md](SPEC.md), [PAR.md](PAR.md), [FFI.md](FFI.md),
[GAPS.md](GAPS.md), [decisions.md](../docs/decisions.md).

## 1. Принцип

У каждого намерения (intent) есть ровно одна каноническая форма. Если две
формы означают одно и то же и выбираются по вкусу автора, одна из них лишняя:
её надо убрать, нормализовать форматтером или оставить только на Go-границе.

Это не «минимум keyword». Keyword можно сделать один, а способов всё равно
останется три. `for` — один keyword, но у него три намерения: обойти
коллекцию, посчитать, крутиться вечно. `or` — один оператор, но у него три
исхода: пробросить, обработать, упасть. Схлопывать разные намерения в одну
форму — это не упрощение, а потеря информации.

Работает обратное: если формы различаются только синтаксическим вкусом и
означают одно и то же, вторая форма запрещена. Примеры настоящих дублей:
`use fmt;` и `use "fmt";`, named и positional struct literal, `or return` и
`if err != nil { return err; }`.

### 1.1. Как решать

1. Одинаковое намерение и одинаковая семантика? Оставить одну форму. Если
   вторая уже есть в грамматике — нормализовать форматтером или запретить.
2. Разная семантика? Это разные намерения. Оставить обе формы и назвать
   различие в документации, а не в голове читателя.
3. Выбор зависит только от данных, а не от вкуса? Сделать его механическим:
   путь содержит `/` — кавычки; expected type известен — bare `nil`.
4. Нужен Go? Это foreign layer, а не второй способ в app-коде. См.
   [FFI.md](FFI.md).

### 1.2. Статусы формы

| Статус | Что значит | Кто отвечает |
|---|---|---|
| canonical | так пишут люди, примеры и документация | язык |
| normalized | парсер принимает, `strizh fmt` переписывает в canonical | форматтер |
| forbidden | парсер или sema отвергает | компилятор |
| foreign | допустимо только в адаптере/Go-слое, не в app-коде | FFI-граница |

Разделение важно: не надо ломать грамматику там, где достаточно форматтера,
и не надо оставлять «deprecated» форму навсегда. Deprecated-форма — это второй
способ с датой смерти.

## 2. Канонические формы

### 2.1. Импорт

```hare
use fmt;
use os;
use strings;
use "charm.land/bubbletea/v2" as tea;
use "./lib" as lib;
use "../shared/config" as config;
```

- Bare identifier — только простой Go-пакет: путь является одним
  идентификатором, без `/`, `.`, `-` и других не-identifier символов, и это
  не local path. `use fmt;`, `use os;`.
- Кавычки — если путь содержит `/` или `.`, либо это local path (`./`, `../`),
  либо путь не является одним идентификатором. Это механическое правило, а
  не выбор: `use "fmt";` — тот же импорт, но неканонический; форматтер
  переписывает его в `use fmt;`.
- Alias — только когда default alias не то имя, которое нужно в коде, или
  default alias невалиден как идентификатор. Default alias — последний
  сегмент пути, `-` заменяется на `_`. Для пути, оканчивающегося на `/v2`,
  default alias равен `v2`; это версия, а не имя пакета, поэтому alias
  обязателен: `use "charm.land/bubbletea/v2" as tea;`. Лишний alias
  (`use fmt as fmt;`) форматтер убирает.
- Local import — всегда путь в кавычках и всегда с alias, если имя директории
  не совпадает с желаемым именем в коде. `use "./lib";` без alias допустим
  только когда пакет называется `lib`.

Почему так: форма пути уже говорит, Go это или local. Кавычки не должны
становиться стилистическим выбором. Частый случай (stdlib) должен быть
коротким, редкий (third-party path) — явным.

**0.2:** `use "fmt";` уже ошибка парсера; канон — `use fmt;`. Alias для
`/v2` пока не обязателен — это надо закрепить в sema или линтере.

### 2.2. Struct literals

```hare
var u = User { Name = "Alice", age = 30 };
var empty = User {};
var p = &User { Name = "Alice" };
var xs = User[] {
    User { Name = "A" },
    User { Name = "B" },
};
```

- Только named fields: `field = value`. Positional `User { "Alice", 30 }`
  запрещён на уровне sema, а не только соглашения.
- Omitted fields получают zero value. Пустой literal `User {}` — канон для
  «все поля zero»; это не ошибка и не требует писать каждое поле.
- Вложенные struct literals тоже named на каждом уровне.
- Map literal — `key = value`; slice/array literal — значения без ключей.
  Смешивать нельзя.
- Go-структуры с unexported полями не собираются literal-ом в app-коде;
  для них есть конструктор в адаптере.

Почему: порядок полей не является API. Positional literal ломается при
вставке поля и прячет, что именно присвоено. Named literal переживает
добавление поля и читается без знания объявления.

**0.2:** sema уже требует `field = value` для struct literal. Концепция это
фиксирует, а не меняет.

### 2.3. Ошибки

```hare
var f = os.Open(path) or return;

var data = read(path) or err {
    if (isNotFound(err)) {
        return u8[] {};
    };
    return err;
};

os.Remove(path) or panic("cannot remove");
```

- `or` — единственный канон проброса ошибок в app-коде. Нет `try`, `catch`,
  `?`, нет `if err != nil` как идиомы.
- `or return` — default: ошибка уходит вызывающему. Это форма для 90% кода.
- `or err { ... }` — только когда здесь есть что сделать: классифицировать,
  повторить, подставить fallback, добавить контекст. Обработчик обязан либо
  вернуть значение/ошибку, либо продолжить в определённом состоянии. Пустой
  обработчик — ошибка ревью, а не «подавить шум».
- `or panic(...)` — только для нарушенного инварианта или падения на старте.
  Ожидаемая ошибка IO/пользователя — не panic. Внутри `par` это не Go panic,
  а ошибка воркера; но канон всё равно `or return`.
- Один fallible call — один statement. `f(g() or return)` запрещён: `or`
  statement-level. Это не временное ограничение, а решение: путь ошибки
  должен быть виден в структуре кода, а не спрятан внутри выражения.
- `or` поддерживает не более одного не-error результата. Для
  `A, B or error` в 0.2 есть только Go-форма
  `var a, b, err = f(); if (err != nil) { return err; };`. Она остаётся на
  FFI-слое: app-код не объявляет такие API и не пишет такой `if`. Если
  Go-функция возвращает несколько значений и error, адаптер заворачивает
  результат в struct или в один `T or error`.
- Ошибку не сравнивают по строке. `errors.Is`/`errors.As` — на границе,
  в адаптере; app-код получает уже осмысленный `error` или свой enum.
  `isNotFound` в примере — helper facade, а не вызов Go-пакета из домена.

**Спорно:** можно вместо запрета расширить `or` на multi-result
(`var a, b = f() or return;`). Это остаётся statement-level и убирает
Go-форму из app-кода, но добавляет кодогенерацию и ещё одно правило
присваивания. Рекомендация — не расширять, пока адаптер решает задачу.

### 2.4. Циклы

```hare
for (var x in xs) { ... };
for (var i, x in xs) { ... };
for (var k, v in m) { ... };

for (var i = 0; i < n; i += 1) { ... };

for () {
    ...
};
```

- Коллекция — range. Обход slice/array/str/map без индексации и без
  `xs[i]` внутри C-style цикла. Для map — `k, v`; для slice — `i, x`, если
  индекс нужен.
- Счётчик — C-style. Когда важна арифметика (`i += 2`, обратный порядок,
  `i < n`), range не выражает намерение; C-style честнее.
- Вечный цикл — `for ()`, с явным выходом (`return` или `break`). Это не
  «while»: отдельного keyword нет, и это осознанно.
- `par for` по map — не канон. У map нет ord, порядок и победитель ошибки
  недетерминированы. Если нужен параллелизм — сначала соберите ключи в
  slice последовательным range, потом `par for` по slice.
- `for ()` внутри `par` — запрещённый паттерн без гарантированного выхода:
  воркер может не завершиться, и `par` не дождётся. В `par` только циклы,
  которые точно заканчиваются.

Почему: `for` один, но намерения три. Если оставить только C-style, range
по map и запись в слот станут шумными; если добавить `while`, появится
четвёртая форма для того же условия.

### 2.5. Параллельность

```hare
par {
    users = loadUsers(id) or return;
    orders = loadOrders(id) or return;
};

par for (var i, url in urls) limit 64 {
    sizes[i] = fetchSize(url) or return;
};

within 30s {
    par for (var i = 0; i < len(urls); i += 1) {
        sizes[i] = fetchSize(urls[i]) or return;
    };
};
```

- `par` — небольшой набор разнородных top-level statements с именованными
  результатами. Один statement — не повод для `par`.
- `par for` — однородные итерации по slice/array/str или C-style счётчику,
  с optional `limit`. Запись — только в disjoint slots, индекс которых
  содержит переменную итерации. Map, указатели, `self`, глобалы — вне
  safe subset (см. [FFI.md](FFI.md)).
- `within` — deadline вокруг области, а не оператор параллельности. Он
  композируется с `par`, `par for` и последовательным кодом; один `within`
  на всю работу, а не по одному на вызов.
- `par` — не `go`: он ждёт, отменяет siblings и возвращает ошибку. Фоновой
  задачи без владельца в app-коде нет; если нужна — это Go-адаптер.
- Ошибка в `par`/`par for`: побеждает низший ord (для slice/array/str и
  C-style — низший индекс). Остальные ошибки теряются. Если нужны все —
  пишите per-slot результаты и сворачивайте последовательно, а не делите
  общий список ошибок между воркерами.
- `defer` на верхнем уровне `par` — отдельный воркер. Если cleanup относится
  к соседним statements, оберните их в блок:

```hare
par {
    {
        defer closeInput();
        work();
    };
    other();
};
```

### 2.6. `nil`

```hare
fn find() *User = {
    return nil;
};

var p = nil[*User];
var xs = u8[] {};
```

- Bare `nil` — когда expected type известен точно: return type, тип
  параметра, тип lhs присваивания, поле struct literal, значение map,
  элемент slice literal.
- `nil[T]` — только когда типа нет или он слишком широкий (`any`,
  интерфейс) и нужно выбрать конкретный nil. Главный случай — `var`:
  `var p = nil[*User];`, потому что у `var` нет аннотации типа.
- Не писать `nil[T]` там, где bare уже типизируется. Не заводить typed temp
  только чтобы избежать `nil[T]`.
- `nil` — отсутствие, `T[] {}` — пустая коллекция, `T {}` — zero struct.
  Это не взаимозаменяемые формы: JSON/API и проверки наличия различают
  nil и empty.
- `nil` допустим только для pointer, slice, map, function, interface. Для
  struct и enum — нет; zero value enum не конструируется.
- Наличие ключа в map — `has(m, k)`, а не `m[k] != nil` и не sentinel.
  Если нужны и значение, и наличие — `var v, ok = m[k];`.

**0.2:** `nil[T]` разрешён всегда, даже при известном expected type. Это
кандидат на warning + autofix, не на жёсткую ошибку: в `any`-контексте
`nil[T]` бывает нужен. Аудит вариантов — в `NIL.md`.

### 2.7. Комментарии

Целевая грамматика: только `//` до конца строки. Блочные `/* ... */`
удаляются. Подробно — §5.

## 3. Что не является дублем

«Один способ» не значит «одна форма на всё». Эти пары похожи, но означают
разное; их нельзя схлопывать.

| Пара | Почему не дубль | Как выбирать |
|---|---|---|
| `var` / `const` | runtime-слот против compile-time значения | `const` — только там, где нужен compile-time (длина массива, case-паттерн) или истинная константа; иначе `var` |
| `T {}` / `&T {}` | значение против указателя; копия против общей идентичности | по типу и владению, не по «удобству» |
| `match` / `if` | исчерпывающий разбор закрытого множества против булева условия | enum/`any` — `match`; условие — `if` |
| `case T` / `case T as k` | проверка типа против связывания значения | значение не нужно — `case T`; нужно — `as k`; `as _` не писать |
| range / C-style `for` | обход коллекции против счётчика | коллекция — range; арифметика индекса — C-style |
| `par` / `par for` / `within` | разнородные задачи / однородные итерации / deadline | по форме работы, не по «что короче» |
| `nil` / `T[] {}` | отсутствие против пустой коллекции | по семантике API; не заменять одно другим |
| `or return` / `or err {}` / `or panic` | проброс / обработка / аварийный выход | по тому, что реально делает код |
| `T[]` / `T[N]` | slice против array | по владению и размеру; это разные типы |

Отдельно:

- `match` с единственным `else` — это замаскированный `if`. Если нужен
  `if`, пишите `if`.
- Цепочка `if` по вариантам enum — это замаскированный `match`, и она
  теряет exhaustiveness. Если множество закрыто, пишите `match`.
- `match`-выражение и `match`-statement — не дубли: в первом значение
  используется, во втором важны эффекты. Если значение не используется,
  statement-форма честнее.
- `T {}` не заменяет `&T {}` и наоборот: methods вызываются через implicit
  pointer, но копирование и sharing — разные намерения.

## 4. Go — foreign layer

App-код не должен видеть Go-специфику. Это не запрет вызывать Go-функции:
`fmt.Println`, `strings.ToUpper`, `sort.Slice`, `os.Open` — нормальные
leaf-вызовы. Запрещено протаскивать Go-формы в API и в модель приложения.

Что считается Go-спецификой:

- `context.Context` в сигнатурах, типах полей и callback-ах;
- `func`, `chan`, `select`, `go`, `sync`, `atomic`, `unsafe`, `cgo`,
  `//go:`-директивы;
- `if err != nil` как способ проброса ошибки;
- импортированные Go-интерфейсы и Go-указатели в публичных полях и
  параметрах домена;
- имена и типы codegen (`zz_strizh.go`, `_s_*`) в прикладном коде.

Правило границы:

- Простая библиотека с leaf-функциями — можно `use` напрямую.
- Сложная библиотека (lifecycle, config, callbacks, context, goroutines,
  глобальное состояние, ошибки, которые надо классифицировать) — только
  через facade. App-код импортирует facade, а не Go-пакет.
- Facade — Strizh-модуль с простыми типами и `or error`. Внутри он может
  делать `use` Go-пакета. Если адаптер должен быть на Go — это отдельный
  binding-модуль; app-код его не импортирует.
- Один и тот же сложный Go-пакет не должен появляться в нескольких
  app-файлах. Если появился — граница уже протекла.

Подробности, допустимый subset, hidden context и `par` — в
[FFI.md](FFI.md).

## 5. Комментарии: line comments only

### 5.1. Решение

- В грамматике остаётся только `// ...` до конца строки.
- `/* ... */` удаляется из языка. Не «deprecated», не «только для
  generated»: в `.str` его нет.
- Комментарий — trivia. Он не привязывается к символу, не является
  doc-комментарием, не влияет на codegen, не участвует в `strizh doc`.
- Комментарий пишет почему, а не что. Закомментированный код удаляется:
  историю хранит VCS.

### 5.2. Почему line-only

- Один delimiter вместо двух и без вопроса, где заканчивается блок. Блочный
  комментарий может скрыть `;`, границу statement и сломать форматирование;
  линейный не может.
- Форматтер сохраняет комментарии по строкам; блочный требует reflow и
  привязки к узлам, а это отдельный класс багов (G46).
- Блочные комментарии провоцируют большие закомментированные куски. При
  line-only удаление видно построчно.

### 5.3. Почему полный запрет комментариев — не упрощение

Соблазн: «нет комментариев — нет проблем». Это упрощает не язык, а
социальную дисциплину.

Семантика — это правила, по которым программа выполняется. Комментарии в них
не входят: запрет не убирает ни одного правила, а добавляет новое.

- Комментарии не участвуют в семантике: имя, тип, control flow, codegen от
  них не зависят. Запрет не убирает ни одного правила языка; он убирает
  единственное место, где записано «почему».
- Без комментариев причина решения уезжает в commit message или issue и
  гниёт. Читатель кода остаётся с «что», но без «почему».
- Запрет не останавливает закомментированный код: его заменят мёртвые
  ветки, строки и флаги. Лечится не запретом, а правилом «не комментируй
  код».
- Generated Go и Go-адаптеры всё равно содержат комментарии, а stack traces
  ссылаются на код. Язык, который их запрещает, создаёт лишнюю границу между
  слоями.
- Настоящее упрощение — один вид комментария, без doc-семантики, без
  директив сборки и без codegen-инструкций. Это и есть line-only.

**0.2:** лексер принимает оба вида, форматтер сохраняет оба. Переход:
warning на `/* */`, затем конвертация в `//` построчно, затем ошибка
парсера. Если внутри блока есть `*/` или код, который нельзя построчно
разложить, — ручная правка, без молчаливой потери.

## 6. Намеренно не поддерживается

Это не backlog. Это решения: если форма не нужна, её нет в языке, а не
«пока не сделали».

| Нет | Вместо | Почему |
|---|---|---|
| local named functions | top-level function или function literal в `var` | второй вид объявления функции, recursion/capture rules; literal покрывает callbacks |
| generic constraints | конкретные функции или Go-адаптер; type params остаются `any` | constraints — второй type system; inference и ошибки растут, а Go уже умеет это в адаптере |
| generic enums | не-generic enum + payload struct или отдельные enum-ы | variant construction и type switch требуют type args; codegen и patterns усложняются |
| guards / struct patterns | `match` + `if` внутри arm; остаются variant fields и `case T as k` | pattern matching — язык внутри языка; guards ломают exhaustiveness, а Go-backend требует отдельный проход |
| lambda inference | явные типы параметров; inference только от expected function type | body-driven inference — bidirectional checking; одно правило «expected type или явно» объясняется лучше |
| expression-level `or` | разбить на statements | скрытый control flow внутри выражения; statement-level делает путь ошибки видимым |
| user variadics | параметр-slice; Go variadics вызываются с `...` | arity overloading и пустой slice; call-side spread уже есть для Go |
| doc comments | обычный `//`; документация живёт в `design/`, `docs/`, README модуля | второй documentation system, который надо парсить, хранить и синхронизировать; компилятор не привязывает комментарии к символам |
| rename / references / code actions | текстовый поиск редактора; LSP остаётся diagnostics/hover/definition/completion/symbols/signature/format | rename через structural interfaces и codegen без полного индекса нечестен; половина rename хуже его отсутствия |
| VSIX | `strizh` LSP + любой клиент; VS Code grammar/client остаются вне core | пакетирование и integration-тесты — отдельный продукт, не язык |
| CLI extras | `build`/`run`/`check`/`test`/`fmt`/`lsp`/`new`/`init`; для race — `-race` | каждый extra — поверхность для поддержки; один binary, один workflow |

Уже отсутствует в app-коде и остаётся отсутствующим: `go`, `chan`, `select`,
`async`, `await`, `try`, `catch`, `unsafe`, `cgo`, `switch`, labeled control
flow. См. §10 в [SPEC.md](SPEC.md).

Это закрывает G12, G15, G16, G17, G19, G22, G24, G25, G42, G47 и G48 как
«не планируется», а не как backlog. Если решение пересматривается, оно
возвращается одной канонической формой, а не набором совместимых вариантов.

## 7. Принуждение

Канон без принуждения — это стиль. Принуждение должно быть в одном месте
для каждого правила.

| Правило | Статус | Где |
|---|---|---|
| `use fmt;`, кавычки только для `/`/`.`/local | canonical | formatter; sema для alias `/v2` |
| named struct literals | forbidden (positional) | sema, уже есть |
| `or` вместо `if err != nil` в app | canonical | review + FFI-правило; multi-result — только адаптер |
| range/C-style/`for ()` по намерению | canonical | review; lint на C-style по slice, если range хватает |
| `par`/`par for`/`within` по намерению | canonical | sema для unsafe `par`; lint на `par` с одним statement |
| bare `nil` при известном типе | canonical | warning + autofix, не error |
| `nil[T]` только когда expected type не фиксирует тип | canonical | warning |
| `match` без `else` для enum | forbidden | sema, уже есть |
| `match` с одним `else` | anti-pattern | lint |
| `if`-цепочка по enum | anti-pattern | lint, если можно доказать |
| map в `par for` | forbidden (target) | sema; сейчас разрешён с ord `-1` |
| `/* */` | forbidden (target) | lexer; уже error |
| doc comments | absent | комментарии не привязаны к символам |
| Go-типы в публичном API | forbidden | review + FFI; линтер по сигнатурам — позже |

Правила, которые меняют смысл, не нормализуются форматтером. Форматтер
переписывает только эквивалентное: `use "fmt";` → `use fmt;`, лишний alias,
отступы. `nil[T]` → `nil` — это sema autofix, потому что нужно знать
expected type. `if err != nil` → `or` — это не autofix: слишком легко
поменять поведение.

## 8. Миграция 0.2 → 1.0

1. **Документация и примеры.** Новые примеры пишутся только каноном.
   Старые — по мере правки, без массового rewrite.
2. **Formatter.** Нормализует импорты, alias, отступы. Блочные комментарии
   конвертирует в `//` построчно, если это безопасно.
3. **Warnings.** `nil[T]` при известном типе, `match` с одним `else`,
   `par` с одним statement, `/* */`, C-style по slice.
4. **Errors.** Positional struct literal уже error. Дальше: `/* */`,
   map в `par for`; expression-level `or` уже error.
5. **Удаление.** Блочные комментарии исчезают из грамматики; deprecated
   форм не остаётся.

0.2 — preview, поэтому ломать можно быстро. Но каждое ужесточение должно
иметь autofix или однозначную замену; иначе это не канон, а запрет.

## 9. Открытые вопросы

- **Multi-result + error.** Расширить `or` до `var a, b = f() or return;`
  или оставить FFI-only? Рекомендация: FFI-only, пока адаптер может
  завернуть результат в struct.
- **`nil[T]` при `any`.** Жёсткая ошибка невозможна: `nil[*T]` иногда
  нужен, чтобы выбрать динамический тип. Warning с исключением для
  `any`/interface.
- **Trailing comments.** Разрешать `x = 1; // ...` или только комментарии
  на отдельной строке? Форматтер сейчас может переносить trailing
  комментарий; line-only это не решает. Решить до 1.0.
- **Map в `par for`.** Запретить совсем или оставить с документированным
  `ord = -1`? Рекомендация: запретить; последовательный range + slice.
- **Порядок импортов.** Группировать stdlib/third-party/local или оставить
  порядок автора? Это стиль, не семантика; если решать — только
  форматтером.
- **Generic constraints.** Если появится реальный use case, добавить один
  канонический синтаксис constraints, а не набор ad-hoc проверок.
