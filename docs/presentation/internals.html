01Общая архитектура

Strizh не пишет машинный код сам. Компилятор переводит .str в Go, а сборку делает обычный go build. Поэтому стандартная библиотека Go и сторонние Go-пакеты доступны через `use`; raw Go — escape hatch, а сложные API лучше прятать за тонким Strizh-фасадом. Всё, что Strizh не проверяет, в итоге проверяет компилятор Go.

Кто за что отвечает

Одна сборка по шагам

  1. driver.Open поднимается вверх до каталога с strizh.toml, читает имя, модуль и версию Go.
  2. Обход проекта собирает все .str и раскладывает их по относительным каталогам: один каталог — один пакет, корень — package main.
  3. Project.Check создаёт go.mod, если его нет, и на время проверки пишет zz_strizh_imports.go с blank-импортами, чтобы go/packages мог найти внешние Go-пакеты. Затем вызывается sema.Check.
  4. gen.Generate пишет по одному zz_strizh.go на пакет, при тестах — zz_strizh_test.go, и копирует runtime в .strizh/runtime/runtime.go.
  5. go build -o ... . собирает корневой пакет. strizh run кладёт бинарник в .strizh/bin/<name>, обычный strizh build — в bin/<name>.
  6. Если Go-компилятор ругается, //line path:line в сгенерированном файле заставляет ошибку указывать на .str, а не на zz_strizh.go.
hello/
  strizh.toml
  main.str
  lib/util.str
  zz_strizh.go
  .strizh/runtime/runtime.go
  .strizh/bin/hello
Важно

Sema проверяет Strizh-правила — импорты, имена, enum, or, par, context, method sets. strizh check затем прогоняет Go typecheck через internal/typecheck: генерирует Go в памяти и получает диагностику go/packages. Поэтому int + string виден уже в strizh check и LSP, а go build остаётся финальным оракулом для build/run/test.

02Lexer и parser

Фронтенд намеренно простой: лексер один раз проходит по байтам и выдаёт токены, парсер — рекурсивный спуск с приоритетами для бинарных операторов. Имена, типы и смысл узлов здесь не проверяются: это работа sema.

Токены и позиции

Токен — это token.Token{Kind, Lit, Pos, End}. Позиция хранит смещение, строку и колонку. Комментарии не попадают в поток токенов: лексер возвращает их отдельным списком, а парсер складывает в ast.File.Comments. Этого хватает formatter'у; doc-комментарии, привязанные к объявлению, не планируются.

  • Литералы: целые, дробные, строки, raw-строки в backticks, rune, duration (30s, 5m).
  • Идентификаторы — Unicode-буквы, цифры и _; ключевые слова Strizh и Go-слова вроде func/range проверяются отдельно.
  • Операторы и пунктуация: =, ==, +=, =>, ..., or и остальные.
  • Ошибка лексера — lexer.Error{Pos, Msg}; парсер добавляет свои ошибки и сортирует всё по смещению, максимум 100 штук.

Точка с запятой

; — настоящий токен, а не автоматическая вставка. Парсер ожидает его после оператора, объявления и блока, использованного как оператор. Если его нет, появляется ошибка expected ';', found ..., после чего парсер пытается восстановиться до конца оператора или объявления. Поэтому блоки if, for, match, par и within в исходнике тоже закрываются с };.

if (ok) {
    run();
};

match (shape) {
case Circle { radius } => area(radius);
case Empty => 0.0;
};

Постфиксные [] и развилка generic/array

Типы наращиваются постфиксно: T[] — срез, T[N] — массив, T[U] — инстанцирование generic-типа. В выражениях x[i] и x[a:b] — это уже индекс и срез. В типовой позиции парсер сначала пробует разобрать список типов, а если не вышло — выражение длины. В выражении x[...] вызов с type args распознаётся только когда за ] идёт (, а аргументы похожи на типы: builtin, несколько аргументов или имя с заглавной буквы. Иначе [...] остаётся индексом или срезом. Если в типовой позиции один аргумент оказался константой, sema нормализует GenericType в ArrayType.

or

or разбирается только на верхнем уровне выражения: аргументы вызовов, условия и вложенные выражения используют parseExprNoOr. Формы три: or return, or panic(...) и or err { ... }. Sema дополнительно требует, чтобы слева был вызов, возвращающий ошибку, а сам or стоял целиком в инициализаторе, правой части, выражении-операторе или возврате. Вложить его в f(g() or return) нельзя: or — statement-level by design.

var f = os.Open(path) or return;
os.Remove(path) or panic("cannot remove");
var n = parse(text) or err {
    fmt.Println(err) or panic();
    return 0;
};

par, match, defer

  • par { ... } — ParStmt с блоком. par for (...) — тот же ForStmt, но с Par: true; limit остаётся выражением в узле.
  • match — MatchExpr. Тело кейса — блок или одно выражение; match считается выражением, только если все кейсы дали выражение. Паттерны простые: литерал, имя, вариант с полями; guard'ов и выражений в паттернах нет — это осознанное ограничение.
  • defer требует вызов, а не произвольное выражение. Область действия — блок; это не Go-дефер на функцию, а запись в DeferStack (см. codegen).

AST

У каждого узла есть Span{Start, End}; End исключающий. Этого достаточно для диагностики, LSP-позиций и //line.

Ошибки с позициями

Ошибки фронтенда всегда несут token.Pos; драйвер добавляет путь файла. Парсер не бросает исключение и не останавливается на первой ошибке: он восстанавливается до ;, } или начала следующего объявления. Несколько реальных сообщений:

expected ';', found '}'
nil requires a type: nil[T]
match is not exhaustive: missing Rect
or must be the whole initializer, right side, statement or return value
writing to total captured from outside par

Go-ошибки после сборки указывают на file.str:line: message: //line подменяет файл и строку. Колонки в директиве нет, поэтому разбор ошибок ограничен — это G34.

03Sema

sema.Check получает разобранные файлы по относительным каталогам и строит Program. Его задача — не проверить все типы, а связать имена, импорты, enum'ы, or, par и hidden context. Всё остальное оставлено Go.

Порядок проходов

  1. collect — объявления пакета, поля, методы, варианты enum'ов, проверка имён и конфликтов.
  2. resolveUses — локальные и Go-импорты, алиасы, проверка конфликтов алиасов.
  3. loadGo — загрузка Go-пакетов через go/packages с Dir = Root; результаты кэшируются.
  4. bindImports, checkCycles — привязка types.Package и поиск циклов локальных импортов.
  5. resolveDecls — сигнатуры функций и типы объявлений; затем тела: checkFuncs, checkTests, checkMain.
  6. colorContext — fixpoint по вызовам для NeedsCtx.
  7. finalChecks — например, неиспользованный импорт.

Пакеты и импорты

Корень проекта — "." и package main; остальные ключи — относительные каталоги через слэш. Локальный импорт обязан начинаться с ./ или ../ и не может выйти за корень проекта. Go-импорт — это путь без ведущей точки; алиас по умолчанию — последний сегмент пути. Один алиас не может указывать на два разных пакета, а неиспользованный импорт — ошибка. Для внешних Go-пакетов драйвер на время проверки создаёт заглушку с blank-импортами, иначе go/packages не увидит зависимость до первого go mod tidy.

Resolve и типы

Ссылки складываются в Ident.Ref и SelectorExpr.Ref: локальная, параметр, глобальная, константа, функция, тип, поле, self, builtin, вариант enum, пакет. Для каждого выражения sema заполняет ExprTypes, для вызова — CallInfo (сколько результатов, есть ли ошибка, нужен ли context). Это же используют hover и completion в LSP.

  • Локальные типы: alias, struct, enum, interface. Alias не создаёт новый Go-тип.
  • Go-типы приходят из go/types и превращаются в ast.GoType или NamedType с PkgAlias.
  • Generic-параметры ведут себя как any: constraints отсутствуют и не планируются, операции вроде < или + может отвергнуть уже Go. Generic enum'ы sema запрещает.
  • Явные type arguments вызова пока не резолвятся: codegen печатает их из сырого AST, поэтому hover/completion по ним слабые (G18).
  • Method sets считаются для локальных struct/interface и Go-типов; присваивание, аргумент, return и элемент composite проверяются на позиции в исходнике (G27). Неименуемые сигнатуры — generics, enum-варианты, массивы, function values, variadic — пропускаются и остаются на go build; явный Go context.Context сравнивается как обычный параметр, hidden-ctx с ним не совпадает.

Enum и exhaustiveness

Enum — это интерфейс с маркерным методом и структуры-варианты. Sema проверяет, что вариант существует, не повторяется и что match покрывает все варианты, если нет _. Голое имя варианта должно быть уникальным в проекте: uniqueVariant ищет его по всем пакетам и сообщает о неоднозначности; квалифицированная форма case pkg.Circle разрешена.

match (shape) {
case Circle { radius } => area(radius);
case Rect { w, h } => w * h;
case Empty => 0.0;
};

Если вариант пропущен, ошибка будет на позиции match: match is not exhaustive: missing Rect. Для не-enum match работает по литералам, именам и константам; _ превращается в default.

or: что разрешает sema

Sema не разворачивает or в код — это делает codegen. Здесь проверяется форма: слева вызов, у вызова CallInfo.HasError, сам or стоит на верхнем уровне, а or return допустим только в функции, которая возвращает ошибку. or поддерживает не более одного не-error результата; or err { ... } заводит err в отдельной области, or panic внутри par разрешён и превращается в ParErrors.Add + cancel + return, package-level инициализаторы с or запрещены.

Write-check для par

Проверка статическая. Для обычного par sema считает captured read/write sets на каждый top-level оператор: у корня может быть один писатель, и никакой другой оператор не может его читать. Для par for запись в захваченный корень запрещена, кроме индексации с переменной итерации: out[i] = ... считается непересекающимся, если цепочка индексов — срез или массив. Локальные переменные, объявленные внутри тела, конфликтов не создают.

  • Запись через захваченный указатель (*p, p.f, p[i], p.M()), в слот map и в self запрещена. Прямые алиасы (var q = p) приписываются корню.
  • return, break, continue не могут пересекать границу par; для выхода — or return/or panic.
  • defer, within и or panic внутри par разрешены: у каждого воркера свой DeferStack и recovery boundary.
  • Не отслеживаются алиасы из полей/индексов и результаты вызовов, записи внутри function literals; вызов метода на захваченном интерфейсе считается записью, а указатель/интерфейс, переданный в свободную или Go-функцию, не отслеживается. Race detector автоматически не включается — go build -race остаётся оракулом (G11).

Context coloring

NeedsCtx — это fixpoint по графу вызовов. Семена: par, par for, within и Go-функции, у которых первый параметр — context.Context. Для каждого вызова sema записывает ребро «вызывающий → вызываемый»; если вызываемому нужен context, вызывающий тоже начинает нуждаться в нём, и так до неподвижной точки. Затем NeedsCtx проставляется на FuncDecl и FuncLit; FuncType и CallInfo получают его из сигнатур и вызовов.

seed: par / within / Go(context.Context, ...)
edge: caller -> callee
rule: callee.NeedsCtx => caller.NeedsCtx

В прикладном коде context не виден: в языке нет отдельного context-типа и параметра ctx, который пишет пользователь. Это внутреннее свойство функции. Codegen сам добавляет первый параметр _s_ctx context.Context и сам подставляет его в вызовы. within подменяет _s_ctx на context с дедлайном внутри блока. На границе Go-интерфейса это перестаёт быть невидимым — см. G10.

Почему это работает не везде

Fixpoint идёт по прямым CallExpr, а не по всем потокам значений. Function values, Go-callback'и, методы интерфейсов, неизвестные типы получателя, package-level инициализаторы и часть тестовых путей могут не получить context (G10). Callback, которому нужен context, но который передаётся в Go, sema отклоняет явно: a callback passed to Go cannot need a context.

internal/typecheck

После чистого parse/sema strizh check и LSP вызывают typecheck.Check: он генерирует Go в памяти тем же internal/gen, подкладывает каждый zz_strizh.go и встроенный runtime через packages.Config.Overlay и загружает пакеты из реального module root. Режим — LoadImports | NeedExportFile, а не LoadTypes: так go list отдаёт export data и не типизирует все зависимости из исходников. Диагностика Go возвращается через //line как Error{Path, Pos, Msg}.

Результат кешируется в памяти по SHA-256 сгенерированных файлов, go.mod, go.sum и runtime; последние 16 результатов. didOpen/didSave запускают проверку, didChange — нет, поэтому ошибки типов очищаются до следующего сохранения. build/run/test не платят за второй typecheck и по-прежнему используют go build/go test. Контракт и пределы — design/TYPECHECK.md.

Структуры и методы

Поля и методы живут в одном объявлении. Метод получает указательный receiver self; голое имя поля внутри метода превращается в self.Field, если его не перекрыли параметром или локальной переменной.

type Counter = struct {
    n: i32,
    fn Inc() void = { n += 1; };
};

type Counter struct { n int32 }

func (self *Counter) Inc() { self.n += 1 }

Enum: интерфейс и варианты

Enum — это sealed interface. Маркерный метод неэкспортируем и реализуется указателем на структуру варианта; снаружи пакета реализовать enum нельзя. Конструирование заворачивает указатель в интерфейс, а match становится type switch'ем.

type Shape = enum {
    Circle { radius: f64 },
    Empty,
};

type Shape interface{ _s_isShape() }
type ShapeCircle struct { radius float64 }
func (*ShapeCircle) _s_isShape() {}
type ShapeEmpty struct{}
func (*ShapeEmpty) _s_isShape() {}
Shape.Circle { radius = 2.0 }
Shape(&ShapeCircle{radius: 2.0})

switch m := (s).(type) {
case *ShapeCircle:
    radius := m.radius
    _ = radius
case *ShapeEmpty:
}

В реальном коде в кейсах есть тело, а bindings полей становятся локальными переменными. Если variant-полей нет, структура пустая; Empty всё равно конструируется как &ShapeEmpty{}.

Ошибки: (T, error) и or

Fallible-функция возвращает Go multi-return: значение плюс error. or не становится исключением — он разворачивается в предикат if err != nil и ранний выход. Для T or error нулевое значение — *new(T); для void or error возвращается только ошибка.

var f = os.Open(path) or return;

_s_v, _s_err := os.Open(path)
if _s_err != nil {
    return nil, _s_err
}
f := _s_v

or err { ... } заводит err := _s_err внутри ветки, or panic("...") превращается в if _s_err != nil { panic("...") }. Если у вызова только ошибка и результат не нужен, получается if _s_err := f(); _s_err != nil { ... }. Имена временных в примере упрощены: настоящий генератор добавляет суффиксы, чтобы не столкнуться с пользовательскими.

Block-scoped defer

Функция, в которой есть defer или within, получает собственный DeferStack. На входе в блок запоминается марка, на выходе вызывается RunTo(mark), а return и break/continue сначала прокручивают стек до нужной марки. Поэтому дефер срабатывает при выходе из блока, а не при выходе из функции.

var _s_d _s_rt.DeferStack
defer _s_d.RunTo(0)

_s_mark := _s_d.Mark()
_s_d.Push(func() { close(f) })
_s_d.RunTo(_s_mark)

_s_d.RunTo(0)
return

Получатель и аргументы defer вычисляются в момент объявления: генератор сохраняет их во временные переменные и только потом кладёт closure в стек. within использует тот же стек, чтобы гарантированно вызвать cancel.

par, par for, within

Обычный par — это WaitGroup и по горутине на top-level оператор. Контекст с context.WithCancel создаётся всегда, даже если тело статически не падает: паника в callee должна отменить соседей. Ошибки хранятся в ParErrors по индексу оператора; побеждает минимальный индекс. У каждого воркера свой DeferStack и recovery boundary: паника превращается в PanicError и отменяет блок. par for дополнительно ограничивает число активных горутин через буферизованный канал (по умолчанию GOMAXPROCS(0)) и захватывает переменные итерации по одной на итерацию.

var _s_wg sync.WaitGroup
_s_ctx, _s_cancel := _s_context.WithCancel(_s_ctx)
var _s_pe _s_rt.ParErrors

_s_wg.Add(2)
go func() {
    defer _s_wg.Done()
    defer func() {
        if r := recover(); r != nil {
            _s_pe.Add(0, _s_rt.NewPanicError(r))
            _s_cancel()
        }
    }()
    var _s_d _s_rt.DeferStack
    defer _s_d.RunTo(0)
    f()
}()
go func() { defer _s_wg.Done(); g() }()
_s_wg.Wait()

if _s_err := _s_pe.First(); _s_err != nil {
    _s_cancel()
    return nil, _s_err
}
_s_cancel()

В реальном выводе каждый оператор завёрнут в блок, а or return внутри горутины делает _s_pe.Add(index, err), cancel() и return из горутины; or panic добавляет ошибку через AsError и тоже возвращает, а не паникует. В void-функции победившая ошибка перепаникуется на выходе из par. within D создаёт context.WithTimeout от контекста воркера, кладёт cancel в его DeferStack и подменяет _s_ctx на время блока.

_s_ctx2, _s_cancel := _s_context.WithTimeout(_s_ctx, 30*_s_time.Second)
_s_mark := _s_d.Mark()
_s_d.Push(_s_cancel)
{
    f(_s_ctx2)
}
_s_d.RunTo(_s_mark)

//line и мусор генератора

Директивы //line path:line ставятся перед объявлениями и операторами. Путь сейчас абсолютный, колонки нет — это G34. go/format переформатирует уже собранный файл, поэтому директива должна пережить форматирование; она переживает, потому что стоит отдельной строкой.

  • G32: в конце функции с результатом может остаться недостижимый panic("unreachable").
  • G33: пользовательский fmt и служебный _s_fmt могут импортировать один путь дважды.
  • G35: GoType.Text иногда ссылается на пакет, которого нет в импортах.
  • G37: файлы перезаписываются целиком, манифеста сгенерированных файлов нет.
  • G38: runtime копируется на каждую сборку, даже если не изменился.

05G10: context на границе Go-интерфейса

Hidden context хорош, пока функция вызывается из Strizh. На границе Go-интерфейса он ломает сигнатуру: Go требует точного совпадения метода, а лишний первый параметр context.Context делает метод несовместимым. Это и есть G10.

Проблема

Допустим, тип Model реализует tea.Model и его Update доходит до par или до Go-функции с context. В Strizh это выглядит так:

type Model = struct {
    fn Update(msg: tea.Msg) tea.Model, tea.Cmd = { ... };
};

Sema ставит NeedsCtx, и наивный codegen выдаёт метод с context-параметром:

func (self *Model) Update(_s_ctx _s_context.Context, msg tea.Msg) (tea.Model, tea.Cmd)

А интерфейс Bubble Tea ожидает ровно это:

type Model interface {
    Init() Cmd
    Update(Msg) (Model, Cmd)
    View() View
}

Без обёртки Go увидел бы лишний ctx-параметр: сигнатуры не совпадают, *Model не реализует tea.Model, и go build падает. Sema (G27) сверяет method set исходного типа и ловит несовпадение сигнатуры до сборки; G10-обёртка сохраняет точную Go-сигнатуру.

Решение 0.2

Статус: 0.2, реализовано

Кодоген генерирует публичный метод с точной Go-сигнатурой и внутреннюю ctx-функцию. Внутри Strizh вызов идёт в ctx-версию, из Go — в публичную обёртку с context.Background(). Через границу пакета или function value дедлайн не переносится.

Публичная обёртка сохраняет точную Go-сигнатуру интерфейса и вызывает внутреннюю свободную функцию, у которой есть context. Внутренняя функция получает receiver явно, поэтому её можно вызвать и из сгенерированного Strizh-кода с текущим _s_ctx.

func (self *Model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
    return _s_ModelUpdate(_s_context.Background(), self, msg)
}

func _s_ModelUpdate(_s_ctx _s_context.Context, self *Model, msg tea.Msg) (tea.Model, tea.Cmd) {
    ...
}

Имена _s_ModelUpdate и _s_ctx здесь иллюстративные; важен shape: экспортируемый метод — ровно сигнатура интерфейса, внутренняя функция — с context. Вызов из Strizh, где context уже есть, должен идти напрямую:

_s_ModelUpdate(_s_ctx, self, msg)

Обёртка с context.Background() нужна для Go-вызова, у которого своего Strizh-context нет. Если Go-вызывающий хочет передать свой context, нужен отдельный adapter/API; интерфейсная сигнатура этого не позволяет.

Почему внутренняя функция свободная, а не метод

  • В Go нет перегрузки: метод Update уже занят публичной сигнатурой. Метод с context обязан называться иначе.
  • Второй метод с context всё равно попадёт в method set типа: он расширяет служебную поверхность, добавляет ещё одно имя, которое надо держать уникальным, и не нужен никому, кроме обёртки.
  • Свободная функция с receiver-параметром — это тело метода без записи в method set: у типа не появляется лишнего метода. Экспортируемая поверхность остаётся ровно той, которую задал пользователь.
  • Внутреннюю функцию проще вызывать из сгенерированного кода: _s_ModelUpdate(_s_ctx, self, msg) не требует ни interface-assertion, ни обёртки.

Та же схема применима к экспортируемым свободным функциям: публичная Foo с точной Go-сигнатурой и внутренняя _s_Foo с context. Для методов это единственный способ одновременно сохранить интерфейс и не потерять отмену.

06Синтаксис 0.2 и кодоген

Не всё уже реализовано

Ниже — раскладка 0.2. Списки результатов, case T as k, else и bare nil реализованы в parser/sema/gen; bin/check их покрывает.

0.2GoСтатус в дереве

Result lists → Go multi-return

Результаты функции — это срез типов, а не один тип плюс ошибка. Генератор печатает их как Go multi-return; return a, b остаётся return a, b. Это уже видно в ast.FuncDecl.Results и resultStr. Список результатов — форма вызова, а не tuple: его нельзя положить в переменную, проиндексировать или передать как один аргумент.

fn split(s: str) str, str = {
    return s, s;
};

func split(s string) (string, string) {
    return s, s
}

Ограничение: or поддерживает не более одного не-error результата. Multi-return нельзя использовать как одно выражение — допустимы return, var a, b = f() и a, b = f(). Это G13.

case T as k → type switch

Для match по any тип-паттерн должен сузить значение и связать его с именем. В Go это обычный type switch; k — переменная с типом T внутри ветки.

match (msg) {
case tea.KeyPressMsg as k => handle(k);
else => ignore();
};

switch k := msg.(type) {
case tea.KeyPressMsg:
    handle(k)
default:
    ignore()
}

else — это default. Для any exhaustiveness невозможна, поэтому else обязателен; enum всё равно должен быть исчерпан, else его не заменяет. Type-паттерны имеют смысл только для any и интерфейсов; enum по-прежнему разбирается variant-паттернами.

Bare nil → typed nil

Bare nil разрешён, когда ожидаемый тип известен: return nil;, f(nil), x = nil. Без контекста нужен явный nil[*Node], nil[error], nil[u8[]]. Генератор печатает (T)(nil), а не *new(T), поэтому значение действительно nil. Допустимы только nilable-типы: указатель, срез, map, функция, интерфейс (G20).

fn stop() tea.Cmd = {
    return nil;
};

var cmd = nil[tea.Cmd];

Почему это нужно Bubble Tea

Update возвращает (tea.Model, tea.Cmd) — два не-error результата; сообщения приходят как any и требуют type switch; Cmd — это функция, для неё нужен typed nil. Без этих трёх вещей tea.Model в Strizh не реализовать. Фоновые таймеры и IO для Bubble Tea не нужны: Cmd запускает сам tea.Program.

07LSP

strizh lsp — тот же бинарник, который говорит JSON-RPC по stdio. Сервер парсит проект, вызывает sema.Check и на open/save запускает typecheck.Check; диагностика публикуется с source strizh. Поэтому LSP видит то же, что strizh check: ошибки парсера, sema и типов Go.

Остатки диагностики (G39, G43–G45)

  • G39. Диагностика типов Go уже приходит на open/save (G26), а strizh check проверяет и test-блоки; остались колонки (G34), async/debounce (G43), test-диагностика в LSP и ошибки вне //line.
  • G43. Анализ синхронный: didChange блокирует цикл сообщений, пока sema обходит проект; debounce и отмены нет.
  • G44. Очередь LSP-обвязки ограничена 64 сообщениями; при быстром наборе didChange может потеряться, и диагностика отстанет до следующей правки.
  • G45. При закрытии файла диагностика не очищается: закрытые файлы продолжают анализироваться с диска, сбрасываются только удалённые и standalone-документы.

Почему это не блокер для Bubble Tea

LSP — инструмент редактирования .str, а не часть рантайма. Авторитетная проверка — strizh check по всему проекту; LSP показывает те же ошибки в редакторе и добавляет базовое редактирование. Языковые блокеры Bubble Tea были в G13 (multi-return) и G14 (type switch по any); 0.2 их закрывает. G10 добавляет обёртку, если Update уходит в par/within. Фоновые таймеры и IO запускает сам tea.Program. LSP можно улучшать отдельно, не меняя язык.

Практический вывод

LSP даёт диагностику, включая typecheck Go, и базовое редактирование. strizh check проверяет весь проект и остаётся источником истины.

08Runtime

Support-пакет называет себя strizhrt, но импортируется как _s_rt. Исходник лежит в runtime/source.go, встраивается в компилятор через //go:embed и при каждой сборке пишется в .strizh/runtime/runtime.go целевого проекта. Это обычный Go-код, не отдельный рантайм языка.

Что внутри

APIЗачем
DeferStack.Mark() intзапомнить текущую длину стека перед входом в блок
DeferStack.Push(fn func())положить отложенный вызов
DeferStack.RunTo(mark int)выполнить всё выше марки в обратном порядке; марка обрезается до допустимого диапазона
Assert(ok bool, pos string)panic с file:line, если условие ложно
AssertEq[T comparable](got, want T, pos string)сравнение с внятным сообщением
Has[K comparable, V any](m map[K]V, k K) boolпроверка наличия ключа для has(m, k)
PanicError{Value, Stack}паника воркера: значение и stack для сообщения и errors.As
NewPanicError(v any)обернуть значение паники и снять debug.Stack() на recovery boundary
ParErrors.Add(index int, err error)потокобезопасно сложить ошибку с номером
ParErrors.First() errorвернуть ошибку с минимальным неотрицательным индексом; -1 — только если других нет

DeferStack

Внутри — срез []func(). Mark возвращает длину, Push добавляет в конец, RunTo(mark) забирает хвост fns[mark:], обрезает срез и вызывает хвост с конца. Поэтому defer'ы выполняются LIFO и не мешают друг другу между блоками и итерациями цикла.

ParErrors

Это мьютекс и срез ParError{Index, Err}. Add игнорирует nil, First выбирает минимальный неотрицательный индекс, а не порядок завершения. Для par индекс — номер top-level оператора, для par for — порядковый номер итерации. Для map-итерации индекса нет: все воркеры отдают -1, и First берёт первую дошедшую ошибку только если неотрицательных записей нет. Порядок map-итерации недетерминирован.

Почему runtime копируется

Сгенерированный Go импортирует <module>/.strizh/runtime, а не пакет из исходников компилятора. Так проект остаётся самодостаточным: его можно собрать без исходников Strizh, и версия runtime всегда совпадает с версией компилятора, который сгенерировал код. Каталог .strizh скрытый, поэтому обход проекта его не парсит. Копирование происходит на каждую сборку, даже если файл не изменился (G38); хеширование и пропуск записи — возможная оптимизация, не обязательная для корректности.

09Тесты

Основной оракул — conformance-программы в tests/cases. Каждый кейс проходит через настоящий компилятор, go build и запуск; сравнение идёт по stdout, а не по мокам внутренних функций. Юнит-тесты лексера, парсера, sema, gen и LSP лежат рядом с пакетами и дополняют эту картину.

Как устроен кейс

tests/cases/par/
  strizh.toml
  main.str
  expected.txt
  • strizh.toml — имя проекта; модуль можно не указывать, драйвер подставит example.com/<name>.
  • main.str — программа с fn main; она печатает то, что сравнивается.
  • expected.txt — ожидаемый stdout, обычно несколько строк.
  • Если есть файл-маркер test, кейс запускается через strizh test, а не strizh run; тогда можно добавить expected-test.txt для строк ok/FAIL.

Что делает tests/run.sh

Скрипт идёт по всем каталогам tests/cases/*, запускает strizh run (или strizh test), сравнивает вывод через diff, затем удаляет .strizh, bin, zz_strizh*.go, go.mod и go.sum. На кейс даётся 120 секунд, на тестовый — 180. Поэтому кейсы можно смело добавлять в репозиторий: они не оставляют мусора.

Как добавить новый кейс

  1. Создайте tests/cases/<name>/ и положите туда strizh.toml с name = "<name>".
  2. Напишите main.str; если нужен тест — добавьте блок test "..." { ... }; и пустой файл test.
  3. Запустите программу вручную и сохраните точный stdout в expected.txt (или expected-test.txt).
  4. После сборки компилятора запустите tests/run.sh или весь bin/check.
test "append grows the slice" {
    var xs = u8[] {};
    xs = append(xs, 1);
    assert_eq(len(xs), 1);
};

bin/check

Единая точка входа: gofmt -l cmd internal runtime, go vet ./..., go test ./..., сборка bin/strizh и tests/run.sh. Во время рефакторинга компилятора этот набор может быть красным; страница описывает код, а не статус CI.

Во время рефакторинга

Не запускайте bin/check как «доказательство» чего-либо, пока идёт переделка. Для отдельного кейса достаточно tests/run.sh после сборки, но и он требует рабочего bin/strizh.

10Границы: что работает и чего нет

Strizh — это 0.2 preview. Страница отделяет подтверждённое кодом от текущих пределов и осознанных отказов. Оставшиеся пробелы — в design/GAPS.md; канонический список отказов — в design/SPEC.md §10.

0.2 — вертикальный срез

  • Публичная обёртка для hidden context на Go-границе (G10).
  • Списки результатов и Go multi-return (G13).
  • case T as k, else, bare nil, match по any (G14, G20).
  • par core: panic recovery, per-worker defer/within, write rules (G1–G9).
  • Typecheck в strizh check и LSP (G26), method sets (G27).

Сознательно не делаем

  • Локальные именованные функции: function literals — единственная форма.
  • Generic constraints и generic enums.
  • Guards, struct-паттерны и user-variadics.
  • Expression-level or: только statement-level.
  • Doc comments, LSP refactors, VSIX и расширенный CLI.

G11 (динамический race oracle), G34 (колонки в //line), G39/G43–G45 (диагностика LSP) и test-диагностика в LSP. Это пределы текущей реализации, а не обещания языка.

Что не блокирует Bubble Tea

LSP и formatter — инструменты, они не участвуют в рантайме. Блокеры Bubble Tea лежали в языке: multi-return (G13) и type switch по any (G14); 0.2 их закрывает. Фоновые таймеры и IO запускает сам tea.Program.
